  neither column moved.

  37 is also exactly the figure S-397 T2 diagnosed as the remaining gap — "37
  sites and every one of them spells `this.`". The prediction and the outcome
  agree to the site.

S-402 T1 — A PRECISION CORRECTION.  26 sites.

  The captured invocation-intake population itself fell 186 -> 160, all of it in
  `hermodr-mirror`, the estate's one Go member, whose captured client-call sites
  went 37 -> 11 when the candidacy gate became receiver-grained. That reproduces
  S-402's own 37 -> 11 measurement independently, through the shipped surface and
  over the whole estate, where S-402 measured it on an isolated copy of the one
  member.

  All 26 were keyless refusals: they produced no reference target and no edge, so
  nothing that bound stopped binding. But the `base-url-runtime` count falls by
  26 for a reason that is not a coverage gain, and every egress denominator falls
  with it.

  Netting the two would report 63 fewer refusals (87 -> 24) as one improvement.
  37 of the 63 are an admission and 26 are a smaller population.

THE ONE NEW `path-not-composed` INVOCATION ROW
-----------------------------------------------

One of the 81 admitted rows refuses under `path-not-composed`. There was no such
invocation row before. It is:

  mailbox-aggregator-api  MailboxApiRestClient#getExportDownloadLink()
  key   mailboxaggregate.api.urigetexportdownloadlink
  value /v1/users/{userId}/mailboxes/{mailboxId}/import-export/download-exported/{job-id}

The estate's PROVIDER half of that same path — the swagger operation in
`software-architecture-documents` — reads `path-not-composed` too, and did
before this change (the contract-surface column's single `unbound` row is
byte-identical across all three generations). So the refusal is symmetric: both
ends decline the same template and no edge is being lost to a one-sided
normalizer.

READ THE WORD CORRECTLY. It is NOT the HTTP arm's "a non-empty stored target that
`route_key` later declined" — `coverage.rs` documents that branch as unreachable
for a store this binary writes, so reading it that way would make this row look
like a stale-binary artefact. A `config-bound` row never reaches it. The word
arrives as the FALLBACK DEFAULT of `record_config_bound`'s
`composed_refusal(&template).map_or(PathNotComposed, …)`: every composition the
resolver proved failed `consumer_portable_key`, and `composed_refusal` had
nothing of its own to say about the template, because the template is a valid
rooted client-call path. One row is not a trend; it is recorded here rather than
chased, and it is not chased in this task, which widened nothing.

A CONTROL RUN WAS TAKEN FIRST, and it is what makes the re-index the only

WHAT A READER SHOULD NOT CONCLUDE
---------------------------------

* Not "the pipeline resolves 81 of the estate's couplings". It admits 81 rows
  carrying a resolved, committed value; 15 of them bind a provider, and none of
  them draws a cross-service edge.
* Not "egress resolution quadrupled". Both terms of that ratio moved, and 26 of
  the 38 sites that left its denominator left for a reason that is not a
  coverage change.
* Not "the refusal count fell by 63, so coverage rose by 63". 37 of the 63 are
  an admission; 26 are a population correction.
* Not "81 is a floor the product now holds". It is what was measured on one
  estate on one date, pinned exactly so a move in either direction is seen.
* Not "the .properties gap is closed". It is open, unowned, and currently free.
* Not "79 was wrong". 79 is a correct census figure and remains one.
