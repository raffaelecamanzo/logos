CR-157 SECTION 3.2 A — QUOTED VERBATIM
--------------------------------------

The whole of part A, character for character, each line indented four spaces:

    **A — Definitions, fixed before the gate runs.**

    - **A1, declaration.** A member **M declares topic T** when a committed value in M's **`src/main` application configuration** equals T, under a **topic-named key**: `spring.kafka.topics.*`, or any key whose last segment is or ends in `topic` / `topics` (`filteraggregate.topic`, `spring.kafka.template.default-topic`). Values are resolved as [S-410](../planning/journal.md#s-410-topic-identity-is-the-committed-configured-value-so-a-streams-publish-meets-a-subscribe) resolves them: one placeholder hop to a committed value, profile-tagged per overlay ([FR-WS-19](../specs/requirements/FR-WS-19.md) AC2). An uncommitted or placeholder-valued result refuses with the existing reasons ([BR-52](../specs/software-spec.md#327-workspace-federation)).
    - **A2, topic identity.** T must be a topic identity the product **captures somewhere in the workspace**, meaning at least one member's broker site resolves to T. A configured value that no broker site names is reported apart as `declared-only`, never as a topic.
    - **A3, net-new pair.** A declaration (M, T) is **net-new** when M has **no observed `Producer` or `Consumer` on T** in the current product. "Current" means the merged-main binary at the run, cluster A included, on a private estate copy.
    - **A4, grain.** `declares-topic(M → T)` is **directionless**. Configuration does not say whether M produces or consumes. It carries `config-declared` provenance: key, defining file, profile set.

HOW EACH TERM OF PART A IS MEASURED — FIXED BEFORE THE RUN
-----------------------------------------------------------

Every instrument below is SHIPPED or S-411 CODE, CALLED. A second copy of any
of them would be a second metric wearing the first one's name.

  1. THE CONFIGURATION READER (A1, "committed value"). S-411's application
     reader, unchanged: the shipped `ConfigCorpus::discover` over the estate
     root, each source folded through S-411's `collect_values` under S-411's
     `Provenance` for the application source set, tagged with
     `identity::application_overlay(profile)`. Keys are therefore in the
     relaxed-binding CANONICAL form the corpus stores (`canonical_key`:
     lower-case, `-` and `_` dropped per segment), and every rule below is
     applied to that form.

  2. "`src/main` APPLICATION CONFIGURATION". A source counts in the decisive
     reading exactly when its corpus-relative path contains the segment pair
     `/src/main/`. The TEST-TREE reading also admits `/src/test/`. An
     application source on neither path is listed with its declarations and is
     counted in NO reading. Deploy overlays are not read at all (B2).

  3. "TOPIC-NAMED KEY". The canonical key starts with `spring.kafka.topics.`, OR
     its last `.`-segment equals `topic` or `topics`, OR its last `.`-segment
     ends in `topic` or `topics`. The KEY-SHAPE SPLIT printed at the headline is
     exactly those three shapes, taken in that order (a key is counted under
     the first shape it matches). A value under any other key is not a
     declaration, however topic-like it is (CR-157 section 3.3, "Any-key value
     equality").

  4. "RESOLVED AS S-410 RESOLVES THEM". The declared value is passed to the
     shipped `resolve::broker_identity::topic_identity` — S-410's function,
     called — over a lookup that sees the DECLARING SOURCE'S OWN MODULE within
     the reading's own sources (the harness's `CorpusLookup` scoping, ADR-64's
     within-reach rule). Its three answers:
       - `Literal`   — no `${...}`: the value is the candidate T;
       - `Committed` — one placeholder hop proved a committed value: each of its
                       topics is a candidate T, carrying the profiles its
                       `ConfigBound` names;
       - `Unresolved`— REFUSED, with the shipped `ValueRefusal` reason
                       (`Uncommitted`, `PlaceholderValue`, `MissingKey`). A
                       refused declaration is never a pair; it is counted apart
                       with its reason.

  5. "A TOPIC IDENTITY THE PRODUCT CAPTURES" (A2). A topic the shipped
     `federation::topics::workspace_topics` read-model lists, over member
     engines opened on the private copy, with at least one producer or one
     consumer, its `#`-guard (a message-schema FQN) stripped. Under the decisive
     reading the workspace is the 83 manifest members. A candidate T no member
     lists is `declared-only` and is never a pair.

  6. "NO OBSERVED PRODUCER OR CONSUMER ON T" (A3). M's own entry in that same
     read-model does not list T with producers + consumers >= 1. Where it does,
     the declaration is ALREADY OBSERVED: counted and listed at the headline,
     never a pair.

  7. THE GRAIN (A4). The distinct (M, T) pair. Several keys, files or profiles
     proving one pair are ONE pair, listed as its evidence (key, file, profile).
     Direction is never read: no key, `default-topic` included, makes M a
     producer or a consumer.

  8. THE B3 SPLIT, per net-new pair, from the shipped
     `federation::coverage::cross_service_coverage` broker rows whose consumer
     endpoint is M, together with M's promoted topics:
       - CONFIG-ONLY    M has no broker row and no promoted topic at all;
       - SITE-REFUSED   M has at least one broker row the product refused
                        (unbound for a reason other than no-provider), printed
                        with its reason and its declaration;
       - SITE-UNCAPTURED otherwise — M has broker sites, none refused, none on T.
     The product's ledger stores no operand for a refused site, so a refusal
     can be tied to M but not provably to T: the split is at MEMBER grain and
     says so beside it. The split never changes the headline count.

  9. THE RECONCILIATION (B3). S-411's own `judgement`, run over the same copy,
     supplies its 13 shared topics and their (member, topic) declarations, which
     S-411 recorded as 36. They are set-compared with this run's declarations,
     and every difference is attributed to a NAMED MECHANISM: the `src/main`
     restriction, the manifest population, the topic-named key rule, member-local
     versus workspace-wide value resolution, the product's captured identities
     versus the harness's, or the declarer threshold (S-411 counted a topic only
     where >= 2 members declare it; A3 counts each pair). A difference no named
     mechanism explains is printed as UNEXPLAINED and FAILS the run.

 10. `filters-ingestion-cdk/cdk.json` is a KNOWN BLIND SPOT (CR-157 section 3.3):
     it is not a configuration source, is never read as one, and is NEVER
     counted. The run names it and states whether it exists on the copy.

A RUN THAT SEES NO ESTATE REPORTS *VOID*, NEVER ZERO
-----------------------------------------------------

Per NFR-CC-04: where `LOGOS_REF_WORKSPACE` is unset the measurement has not been
performed. The estate arm prints VOID and asserts nothing about the gate. The
classifier deciding declared / observed / net-new carries ALWAYS-RUN fixtures,
independent of the estate: a declaration with an observed Producer on the same
topic is observed; a declaration with no site on T is net-new; a value no broker
site names is declared-only; a placeholder or uncommitted value is refused; an
estate-blind run is VOID.
