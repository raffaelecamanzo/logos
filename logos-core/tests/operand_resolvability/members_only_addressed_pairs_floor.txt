WHAT "MEMBERS-ONLY" MEANS IN THE HARNESS, EXACTLY
--------------------------------------------------

The identity registry is S-384's `identity::Corpus`, judged through S-384's
`Corpus::member_for` (FR-WS-20 AC2 as written) by S-411's `label_state` and
`classify_pair`, all CALLED. The one change is to the CLAIMS that corpus holds:

  1. A claim at tier 1 (deploy), tier 2 (container) or tier 3 (directory) is
     kept only when its member is one of the 83 listed below. A label that only
     a non-member claims at those tiers is therefore no identity, and a value
     naming it falls in the existing "label resolves to no member" bucket; a
     collision at those tiers is counted only between members.
  2. Claims at tier 4 (`spring.application.name`) and tier 5 (artifact id) are
     kept EXACTLY as S-384 records them, from every directory. CR-158 says
     "Tiers 4–5 stay recorded and never decisive, as today"; in the S-384
     classifier as it runs today tier 5 is never decisive but TIER 4 IS
     (`Tier::is_decisive` excludes only `Artifact`). This declaration resolves
     that against the CR's own scope sentence — "Tier 1–3 identity labels ...
     are collected only from the members" — and leaves tier 4 as today. The run
     PRINTS how many judged targets and STRICT pairs would move if tier 4 were
     scoped too: a report, never counted.
  3. Nothing else in the corpus changes: the target references, the walk, the
     Spring key census.

THE PATH-ONLY SUBTRACTION, TAKEN WITHOUT THE FORK. CR-158 section 3.2 A requires
"the path-only subtraction, taken over the same population the pairs are counted
over, so the fork's duplicate routes take no part". In the harness that means,
exactly: the path-only set is S-384's own consumer-site judgement (its `judge`,
FR-WS-20 AC2 literal resolution, CALLED, never copied), run

  - with the members-only registry above, so a site addressing `archive-api`
    now names a provider; and
  - against S-384's provider index restricted to the 83 members, so a route the
    fork alone duplicates no longer makes the template ambiguous;

and its "already bound by path alone" (consumer, provider) pairs are the
subtracted set. It is the decisive population's subtraction and it is applied
to all three readings, exactly as S-475 applied S-411's one path-only set to
all three. The runnable rule is S-411's runnable set, unchanged.

FOR EACH OF THE TWO AGGREGATOR PAIRS the run prints whether this fork-free
subtraction KEPT or REMOVED it and, when removed, the path-only binding — the
consumer site, its normalized template, the via-key and the overlay — that
caused it:

    funnel-aggregator-api  -> archive-api
    mailbox-aggregator-api -> archive-api

The outcome is NOT predetermined (CR-158 section 2.1): with both pairs the
STRICT reading would be 13, with one 12, with neither 11. That arithmetic is the
CR's expectation, recorded so the run can be read against it, and it is NOT an
acceptance figure.
