  one question this run leaves genuinely open, and it is a stakeholder
  population decision (CR-153 CRA-02), not a reader question.

  THE FIRST RUN FAILED, AND WHY THAT WAS THE CHECK WORKING

  The first estate run of this gate FAILED on 233 collapsed keys, all in Helm
  `templates/deployment*.yaml`. There a column-0 directive (`{{- range … }}`,
  `{{- end }}`) cuts a container item in two. The SHIPPED parser then hangs the
  item's remaining lines under the enclosing key — `spec.template.spec.
  containers.image` is a key it produces today, the `routes:` fabrication still
  live on templates — while the rewrite hung them under the item. So the rewrite
  changed shipped keys and nested one sentinel inside another.

  The reader now REFUSES such a source whole: where the rewritten text, outside
  every item, does not read key-for-key as the shipped parser reads the original,
  the source adds nothing. That is the under-read direction the declaration
  allows ("each chosen so the reading can only UNDER-read"), and what it costs is
  measured rather than argued:

    sources refused                                        32   all Helm templates/deployment*.yaml
    item keys those sources would have added              242
    target values they would have admitted                  0
    addressed pairs they would have added                   0

  and the three readings are identical before and after the change (13 / 12 / 11
  on both runs). An index-free key on a source the reader does NOT refuse still
  fails the run. The two checks do not separate reader defects from source
  shapes: a leaked item line lands outside every item and refuses its source,
  exactly like a template. What guards against a refusal hiding a defect is the
  pinned refusal count, the forgone targets (0) and the items bound.

  THIS REFUSAL WAS ADDED AFTER THE DECLARATION. The declaration committed at
  2026-09-29T09:17:07Z defines a change to a shipped key as a collapsed key that
  fails the run, and names no refusal. The first run failed on exactly that
  (233 keys, all Helm templates); the whole-source refusal came after it. Its
  measured cost is 0 target values and 0 pairs, and the readings did not move,
  so the verdict does not depend on it — but whether to accept it as a reader
  restriction or restore the declared semantics is a stakeholder decision,
  recorded here and in ADR-65's appendix, not taken by this run.

  FOR S-476: the shipped `parse_yaml` fabricates `spec.template.spec.containers.
  image` (and siblings) on every Helm deployment template on this estate. S-411's
  metric consumed those keys unchanged, and none of them is target-valued, so no
  recorded figure moves; but a product flattener that reads items (S-476) would
  inherit the same ambiguity and must decide it, not this gate.
