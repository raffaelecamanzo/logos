THE RECEIVER RULE, AND WHY THE FIRST TWO RUNS OF THIS HARNESS WERE WRONG

  Recorded because the numbers this file reports depend on it entirely, and
  because both faults were found by running the harness against the estate
  rather than by reading it.

  RUN 1 reported 0 of 13, with all seven named sites refused as "3+ frames".
  Cause: frame two looks up `ArchiveEventKafkaProducer.sendMessage/3` and finds
  the `super.sendMessage(…)` line INSIDE that very method, whose argument is
  that method's own parameter. A method's own body is not a caller of it.

  RUN 2 reported 8 of 13 with five sites refused as "3+ frames". Cause: with two
  sibling producers in one module, following either one's forward picked up the
  OTHER's `super.sendMessage(…)` line as a phantom caller.

  Both are one fault: `super.m(…)` written inside `class C extends B` calls
  `B.m`, and binding on (name, arity) alone cannot see that. The rule now
  applied — `dispatches_past` — is decidable from the tokens and adds no type
  inference: a `super` call is a caller of the method frame two is looking up
  only when that method is declared in the class the call dispatches to. It is
  the "receiver-aware" CR-131 C2 already specifies.

  The direction that must NOT be over-excluded is pinned too: a three-class
  chain where `Deep extends Middle<K, V>` forwards through `super` keeps its
  real caller and refuses for its LENGTH, not for "no call site". That fixture
  fails if `simple_type_name` reads the wrong child of a `generic_type` — the
  shape the estate writes as
  `extends KafkaProducer<ArchiveEventKafkaKey, SpecificRecord>`.

  A THIRD instance of the same fault was found at review, in the other
  direction: both class walks climbed past an ANONYMOUS class body
  (`object_creation_expression -> class_body`) to the enclosing named class, so a
  `super.send(…)` inside `new Thin() { … }` was attributed to whatever the OUTER
  class extends and the real caller was discarded. Discarding callers RAISES the
  resolved count, so this one was not on the safe side — and the doc comment said
  it was. Both walks now stop at an anonymous body, `enclosing_superclass_name`
  reads the instantiated type there, and a fixture pins it. Not reachable on this
  estate (no anonymous subclass of a producer base writes `super.sendMessage`),
  so no recorded figure moves; recorded because S-417 would inherit it.

  A fourth, in the evidence rather than the measurement: the signature census
  that attributes each refusal was read off the files the `Calls` ledger names as
  CALLERS of a forwarding method. A method's declaration is almost never in a
  file that calls it, so the count came back 0 for exactly the modules it
  describes, and it counted the bare NAME across every arity and both trees while
  frame two binds on (name, arity) in `src/main`. It is now a declaration walk
  over every main-tree source, keyed on the signature. The five refusals were
  correctly attributed before and after — the figure was right by luck, because
  the frame-one whole-estate walk happened to cover the same name — but nothing
  made it so.

WAS THE FLOOR BADLY CHOSEN?

  It is not revised after the run and it stands unchanged. The question still
  deserves an answer rather than a silence.

  The floor is cleared by 1. That is close, and closeness is worth stating
  plainly rather than rounding away: had the second frame bought 0 instead of 2,
  the reading would have been 6 and the gate would have FAILED. So this gate
  turned on the second frame doing something, which is exactly what it was for,
  and V6 is why "it did something" is asserted rather than inferred from the
  headline.

  What the result does NOT turn on is the choice of 7. A floor anywhere from 7
  to 8 is cleared; 9 or above is not. The number was taken unchanged from S-392
  precisely so that this could be said — re-deriving a floor for a re-proposal
  is how a gate gets quietly lowered to fit what the second attempt can reach.

  The honest summary: the gate passes by one, on a figure that is SOUND where it
  resolves (both second-frame resolutions drawn from pools that cannot mix,
  asserted) and a LOWER BOUND where it refuses (all five refusals attributable to
