RECOMMENDATION — DO NOT FILE TYPESCRIPT RECEIVER TYPING (advisory)
-----------------------------------------------------------------

On the stated denominator a declared-type receiver rule — CR-150's approach,
transposed — reaches at most 20 of 452 unresolved rows (4.4 %). If every one of
them bound, first-party .ts method-form resolution would move from 58 of 510
(11.4 %) to at most 78 of 510 (15.3 %). Adding the initialiser inference that is
NOT a declared-type rule (Angular `inject(T)`, `new T()`) lifts the bound to 38
(8.4 %). All 20 sit in one member, pec-agid-statistics-informer, the estate's only
first-party TypeScript application. Precision is not what limits it (0 ambiguous,
0 self-ties); reach is, and the residue is not reach a receiver-typing rule can buy:

  - 96 library/global receivers (cy 20, Number 15, Object 9, Math 6, console 5 …;
    26 package imports: TestBed, Logger, …) — never bindable (NFR-RA-05).
  - 38 of the 50 typed `this.f` receivers name a library type (HttpClient,
    WritableSignal, ChangeDetectorRef, HttpService …); so do 27 of the 30 typed
    locals/parameters (ComponentFixture …) and 3 `new T()` receivers (Date).
  - 117 call-result receivers (`.pipe().subscribe()`, `expect(x).toBe()`) need
    return-type inference, which no declared-type rule provides.
  - 18 rows are Angular signal reads `this.x()`: the method name is a Field of the
    caller's own class, so a callable-binding rule correctly refuses them.

Re-entry condition: revisit when CR-150 has shipped a reusable receiver-typing
mechanism for Java (making a TypeScript port cheap), or when an estate carries a
first-party TypeScript population large enough that 4.4 % is material. This figure
is an upper bound from one estate — never a floor or an acceptance target for any
later story.


THE UPPER BOUND, AND WHY IT IS ONE
----------------------------------

Every judgement call is resolved toward binding:
  - typing is file-scoped: shadowing is ignored, and an unannotated declaration of
    the same name never poisons an annotated one;
  - a type is matched by NAME across the member, not through the import path —
    the one first-party .js "cross-class" pair binds only because
    `const addresbook_page = require('../pages/AddressbookPage')` happens to share
    its name with the class that module instantiates (`module.exports = new
    addresbook_page()`): right answer, wrong reason;
  - a method a type lacks is looked up through the type's source `extends` chain
    (CR-150 section 3.2 B), up to 8 hops; the TypeScript plugins record no Extends
    edge, so a shipped rule would first need one.

Outcome split, first-party .ts (452):
  would bind 20 (cross-class 20: 12 typed `this.f` — e.g. this.agidService.sendP01Report,
    this.mailboxesService.getStatisticsForPeriod; 5 imported static calls —
    P01RequestBody.Build, P02RequestBody.Build; 3 typed locals/parameters —
    breadcrumbsService.getBreadcrumbs, headers.getHeadersAsArray)
  miss: type not declared in the member 94 · the member is a field 18 · no receiver
    type 320 · ambiguous 0

Outcome split, first-party .js (258): would bind 86 — 84 via supertype (webmail
