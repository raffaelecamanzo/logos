  client-name boundary rule — the same rule shape a port would apply, which is

  because `dedup_sort_refs` collapses per declaration.

  A CORRECTION MADE DURING THIS MEASUREMENT, recorded because it moved a
  figure. The first run classified `reqwest::Client::new().get(…)` as
  non-HTTP: the reducer took the receiver's last segment, and that is `new()`.
  Three genuine reqwest calls sat in the non-HTTP column, and the headline read
  121 (41%) instead of 118 (40%). The fix distinguishes the two separator
  classes — a `.` accesses a value on another value, so only the LAST one names
  the receiver (`client.headers()` is a header map, not a client), while a `::`
  qualifies one type path, so EVERY segment of it names the same thing. Pinned
  on both edges by `the_receiver_reduction_handles_each_arms_spelling`.

  TWO FURTHER CORRECTIONS CAME OUT OF REVIEW, and neither moved a figure — the
  whole table above was re-run afterwards and is byte-identical, census
  included. They are recorded because of WHEN they would have fired, not
  because of what they changed here:

  1. The cut was taken at the separator's START index, so the `.` inside `?.`
     and `&.` won and the receiver kept a dangling sigil (`httpClient?`), which
     defeats both naming rules. Ruby's `&.` was not in the separator set at all,
     and C#'s `await` was absorbed into the receiver slice. All three land a
     GENUINE client call in the non-HTTP column — the direction that inflates
     the share this gate reads. Rust has no safe call and the three languages
     that do were all GATE-UNEXERCISED, so nothing above moved; the defect
     would have fired on the first re-measurement THIS DOCUMENT ASKS FOR.
  2. `LanguageRegistry::load` was given the corpus root, which is also the
     plugin-override root, so a `.logos/plugins/rust/queries/invocations.scm`
     inside a corpus silently replaced the query being measured. Demonstrated
     to turn a 3-site/1-non-HTTP corpus into `0 (0%)` and print `CLOSES OUT`,
     exit 0, with nothing in the report disclosing it.

  Both were invisible to the suite when they were written: `receiver_of` had no
  corpus-free test, so replacing its body with `return None` left every test
  green while a real measurement classified every site non-HTTP. It now runs
  through each arm's real grammar in plain/safe-called pairs.


RUBY — MEASURED, and the corpus decides nothing.

210 files, ONE admitted by the ledger gate, ONE captured site:

  Gems/2.6.0/gems/xmlrpc-0.3.0/lib/xmlrpc/client.rb:540 — `pairs.delete(cookie.name)`

`pairs` is a Hash built four lines above; `delete` is `Hash#delete`. It is a

n=1 is not a basis for a port: one site cannot distinguish "this language has

  That judgement is in the harness, not only in this file, and it applies in

  was consulted, so a single client-named site printed the terminal "no port is
  justified here". Ruby measured exactly one site — had that site's receiver

  about when a proportion stops carrying information — NOT as an acceptance

  English sentence. The first draft of this module had no floor and printed

S-402'S TRAP, IN THESE FIGURES.

CR-128 §4.4: "a fixture whose receiver the new rule refuses stops testing the
ledger gate, because its positive control becomes unreachable." A
gate-isolating fixture works by showing that the same source captures WITH the
client import and not without it. If a later receiver rule refuses that
fixture's receiver, both halves go silent together and the fixture keeps
passing while testing nothing.

It bears on this table in a way a reader cannot see from the numbers: EVERY one
of the 118 non-HTTP-named rust sites is a site a receiver rule would refuse,
and any of them may be serving somewhere as a positive control. The census is
therefore an input to a port, not only its justification — a port reads it to
find which receivers stay ACCEPTED, and re-points its gate-isolating fixture at
one of those. On this corpus the receivers that stay accepted are `client`
(152), `http` (8), `self.client` (5), `self .http_client` (4), `http_client`
(3) and `reqwest::Client::new()` (3).

Rust's own new pin is written against the trap. Its positive control is the
bare word `client` — the one receiver spelling both shipped receiver rules
(Java's S-375, Go's S-402) accept WHOLE — so when a port lands, the control
survives and the ceiling half is what moves. This was verified, not assumed: a
prototype receiver rule (`#match? @_recv "^(client|http|http_client)$"`) was
applied to `rust/queries/invocations.scm` and the pin failed with
`left: ["GET /api/orders"] right: ["GET /api/orders", "GET /config/features"]`
— the ceiling gone, the control standing. The two halves are two tests
(`a_non_client_receiver_call_inside_a_reqwest_file_is_a_stated_ceiling` and
`a_route_shaped_get_outside_a_reqwest_file_is_not_captured`) rather than one,
so a rule that silenced both would show as one failing and one passing rather
than as a green run.

The pin's fixtures use the shapes the census actually found, per CR-128 §6:
`headers.get("content-type")` is the single largest bucket (54 of 99) and
`router.get("/config/features")` is the `HashMap` lookup at
`matchit-0.7.3/examples/hyper.rs:38`. They pin the two harms separately — the
router lookup becomes a fabricated REFERENCE because its argument is an
absolute-path literal, the header lookup a REFUSAL ROW because its argument is
not.


WHAT IS FILED, AND WHAT IS NOT.

CR-128 §6 criterion 1 is a blocking gate: nothing below it is built for a
language that does not clear it. Per language, from the measurement and from
nothing else:

  rust      CLEARS. 40% of captured sites on receivers no client rule accepts,
            99 of them unambiguously not HTTP calls, producing 69 references
            and 130 refusal rows over the corpus. A receiver-rule port is
            justified and should be filed.
  ruby      DOES NOT CLEAR — measured, n=1. Re-measure on a corpus with real
            client code before filing anything.
  kotlin    DOES NOT CLEAR — gate unexercised, no corpus.
  php       DOES NOT CLEAR — gate unexercised, no corpus.
  c-sharp   DOES NOT CLEAR — gate unexercised, no corpus.

No port story is written here for the four that do not clear, and no
requirement is written for any of them. CR-128 §5.1 wrote none at filing for
exactly this reason: a CR that pre-writes a requirement leaves the
specification mandating an unbuilt capability when its blocking measurement
closes it out, which is the failure CR-113 left in five live locations. The
delivery story writes down what it built.

Note for whoever files rust's port: its expected site-count drop is NOT 118.
The 19 ambiguous sites include genuine calls a name rule would newly refuse, so
the drop is bounded below by 99 and above by 118, and the surviving count must
be re-enumerated after the change rather than predicted — S-375's "genuine
count does not fall" criterion, re-applied. Record the drop as a precision
correction per CR-110, as S-402 did at 37 -> 11.

`rust` gains its stated-ceiling pin regardless of any of this, per CR-128 §6's
sixth criterion — it is the only one of the six arms with no pin at all, and an
unpinned ceiling is prose, which cannot fail. That pin is in this module and
does not depend on a corpus.
