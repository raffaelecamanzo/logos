THE ONE CHANGE: THE ITEM-SCOPED SEQUENCE READING (CR-153 SECTION 3.2 A)
------------------------------------------------------------------------

S-411's declaration wrote down, before its run, that the shipped `parse_yaml`
binds no scalar under a YAML SEQUENCE. This run changes exactly that and nothing
else. Every YAML source in both source sets is read as

    what the shipped `parse_yaml` reads, UNCHANGED, key for key and value for
    value
  PLUS
    the scalars of each sequence item, bound under an ITEM-SCOPED KEY.

An ITEM-SCOPED KEY carries the item's zero-based position in its sequence as a
bracketed index on the sequence's own key: `proxy.upstreams[0].host`,
`proxy.upstreams[0].port`, `proxy.upstreams[1].host`. Its mapping segments are
canonicalised by the existing relaxed-binding `canonical_key`; the index is never
normalised away. A sequence item carries the overlay tag of the file that holds
it.

Three rules, each chosen so the reading can only UNDER-read, never fabricate:

  1. NEVER COLLAPSE THE INDEX. A key without its index (`proxy.upstreams.host`)
     is never produced. That is precisely the fabrication the shipped
     flattener's doc comment records: a `routes:` list that invented a
     `spring.cloud.gateway.routes.uri` key out of a list element.
  2. SCALARS IN AN ITEM BIND ONLY UNDER THAT ITEM. An item's continuation lines
     never register as children of the enclosing mapping.
  3. A SCALAR SEQUENCE (`- value`) BINDS UNDER `key[i]`. Nested sequences, block
     scalars, flow sequences (`[a, b]`) and flow mappings (`{a: b}`) stay
     UNBOUND, as they are today.

One further restriction, stated so it cannot be read as a finding about the
estate: a sequence binds only when the line immediately before its first item
(comments and blank lines aside) is the mapping key whose value it is. A sequence
at the document root, or one whose key the shipped parser does not read, has no
key to scope its items under and stays unbound, counted.

"COLLAPSED KEY" MEANS, EXACTLY. Any key the sequence reading adds to a source
that is NOT item-scoped, or any change the sequence reading makes to a key or a
value the shipped `parse_yaml` produces for the same source. Either is a
fabrication, and ANY collapsed key on ANY source FAILS THE RUN — it is an
assertion, not a report line.

THE THREE READINGS, AND WHICH ONE DECIDES
------------------------------------------

Every run prints all three, side by side, each against the floor:

  DIRECTORY   the 84 `.git` directories — S-411's population, through the new
              reader. Printed for comparability with S-411. NEVER decisive.
  MANIFEST    the 83 manifest members listed above, test-harness consumer
              counted — CR-153 B4's "manifest population" figure.
  STRICT      the manifest population with the TEST-HARNESS CONSUMER not counted:
              no pair whose A is `e2e-tests` (the end-to-end suite whose
              `final-tests/` docker-compose S-411 counted and flagged). The
              runnable rule constrains only the TARGET, so this is the one
              consumer the metric admits that is not a production deployment.

THE DECISIVE READING IS STRICT. CR-153 section 3.2 B4 fixes this, before the run:
"HOLDS only on the directory population or only by counting `e2e-tests`" is
"recorded FALSIFIED on the decisive reading". So:

  HOLDS      STRICT >= 12. (STRICT is a subset of MANIFEST, so MANIFEST also
             holds.)
  FALSIFIED  STRICT < 12, whatever DIRECTORY or MANIFEST read — and when either
             of them reaches the floor, the record says which, beside the
             verdict, so the stakeholder can re-decide the population in a later
             CR and not in this run.
